# 识别卡片非匀速进度设计

## 目标

将微信小程序每张识别卡片当前基于 15 秒线性增长的进度，改为总时长 6 秒的分段加速进度。动画前段推进较慢，中后段明显加快，同时仍以真实识别结果决定完成状态。

## 已确认方案

- 排队状态显示 `0%`。
- 开始处理时显示 `8%`。
- 以任务启动时间为基准，在 6 秒内按以下节点推进：

| 已用时间 | 显示进度 |
| ---: | ---: |
| 0ms | 8% |
| 1500ms | 15% |
| 3000ms | 32% |
| 4500ms | 62% |
| 6000ms | 92% |

- 相邻节点之间使用线性插值，页面仍每 300ms 更新一次，因此视觉上连续但整体节奏非均匀。
- 真实识别在 6 秒内完成时立即变为 `100%`，不强制等待动画走满。
- 6 秒后真实识别仍未完成时停在 `92%`，不伪造完成。
- 识别失败时保留失败瞬间的进度并切换为失败状态。
- 重试时重置为 `0%`，下一次开始处理时重新从 `8%` 运行。
- 跳过、任务结束、页面销毁或切换到下一任务时清理计时器。
- 不改变现有串行识别、图片处理和服务端请求逻辑。

## 实现边界

在 `miniprogram/domain/recognition-queue.ts` 中保留纯函数：

```ts
getTimedRecognitionProgress(elapsedMs: number, durationMs?: number): number
```

默认总时长改为 `6000ms`。函数按上述节点做分段线性插值；负时间按 0 处理，超过总时长封顶 `92%`。如果测试传入自定义总时长，各节点按总时长的 `0%、25%、50%、75%、100%` 等比例缩放。

页面层继续用任务真实启动时间计算 `elapsedMs`，不通过逐次累加百分比推进，避免定时器延迟导致总时长漂移。

## 验收标准

1. 默认进度总时长为 `6000ms`。
2. 0、1.5、3、4.5、6 秒分别返回 8、15、32、62、92。
3. 节点之间的进度单调递增且按对应分段插值，不再均匀分配。
4. `preparing → recognizing` 状态切换不能让进度倒退。
5. 完成立即 100%，失败保留当前值，重试归零。
6. 页面继续正确启动、推进、停止和销毁清理计时器。
7. 专项测试、TypeScript 检查和 `git diff --check` 通过。
